### 步骤 1（人工）：推导你自己的阶段模型

#### 19 阶段推测列表的考证（被推翻的原始版本）

那个"凭空想的 19 阶段列表"在 git 历史里：**首个 commit `48311bed`（2026-06-05，Scaffold kuna）的根目录 `STAGES.md`**，全文只有两行（`git show 48311bed:STAGES.md`）：

```
## Speculated Decompiler Stages
Phase 1: Frontend (Bytes to IR), 00 Loader, 01 Decode, 02 P-code Lift, 03 Disassembly,
04 IR Containers, Phase 2: Analysis, 05 Simplify, 06 Dataflow, 07 SSA, 08 Calls,
09 Stack, 10 Memory, 11 Scalar Types, 12 Aggregate Types, 13 Variables, 14 Range,
15 Interproc, Phase 3: Backend (Structure and Emit), 16 Structuring, 17 C Lowering,
18 C Render
```

一个编译器式的三段前馈模型：前端（Loader/Decode/P-code Lift/Disassembly/IR 容器）→ 分析（Simplify/Dataflow/SSA/Calls/Stack/Memory/标量类型/聚合类型/Variables/Range/Interproc）→ 后端（Structuring/C Lowering/C Render）。

**被推翻的方式（`ed1ae4d8` 的对比）**：新 `STAGES.md` 开头直接写死因——*"This replaces the earlier speculative 19-stage compiler-like list. A decompiler is not a feed-forward pipeline"*。证据研究发现的三个事实结构性地否定了它：

1. **前馈模型是错的**——Ghidra 有 9 种反馈环（restart、mainloop 重跑、opcode 触发的重分析），19 阶段列表表达不了任何一种；
2. **05–14 这段在 Ghidra 里没有阶段边界**——S3–S6 四个工件在同一个 `mainloop` 里共同演化（Band B 互不动点带），把 SSA(07)/Calls(08)/Types(11)/Variables(13) 列成独立阶段是对 Ghidra 代码的错误切分；
3. **缺正交知识平面 P0**——Ghidra 的 Symbol DB/Override 被每个阶段读，不属任何一段。

值得注意的细节：推测版（06-05）和证据版（06-06）**同一天先后存在**——推测版是 scaffold commit 的一部分，即"先想一个框架占位，再用证据研究替换它"是**有意的流程，不是失误**。19 阶段里的大部分名字（Loader/Decode/Lift/SSA/Calls/Types/Variables/Structuring/Render）活进了 P1–P9——**死的是分组假设（三段前馈）和 Band B 的边界，不是阶段名**。

（教训：占位框架的价值是给第一天的读码 agent 一个"对照并推翻"的靶子；它被推翻得越彻底，证据研究越可信。）

#### 1a. 证据档案的生成机制（docs/evidence/ 的原版形态）

原版 `ed1ae4d8` 的提交说明写明：*"Replaces the speculative 19-stage list with the evidence-derived model (raw reports in docs/evidence/)"*——**先用人工凭空想了一个 19 阶段列表，被这次证据研究推翻替换**。这是本项目第一个 agent fan-out（比 Rust 移植的 wave fan-out 早四天），分三层：

**第一层：10 份探索报告**（"10 parallel readers, structured schema"）——10 个并行 agent 会话，每个读一个反编译器的一个切面的源码树，按统一 5 字段 schema 输出（`pipeline`（带 anchor 的有序步骤）/`feedback_loops`/`decision_points`/`intervention_surfaces`/`insights`）：

| 文件 | 对象 | 切面 |
|---|---|---|
| `00`–`03.json` | Ghidra C++（读本 repo vendor 的 `decompiler/cpp/`） | Action/Rule 引擎与调度 → 前端（流跟踪/跳表）→ 中端（SSA/prototype）→ 类型/变量/结构化/输出 |
| `04`–`07.json` | angr（读 `angr/angr/analyses/decompiler/`） | pipeline/Clinic → OptimizationPass 体系 → 结构化（RegionIdentifier/SAILR）→ options/KnowledgeBase |
| `08`–`09.json` | Reko（读 `reko/src/`） | driver phases → 数据流/SCC/类型 |

**第二层：3 份竞争提案**——A（工件中心透镜：SSA-as-property、正交 P0、region/CFG 分离）、B（决策中心透镜：断言目录、HARD/HINT、LATENT）、C（调度中心透镜：机制类型学、回卷范围），**强行要求透镜不同**。

**第三层：2 份对抗批评**——`critique-coverage.json`（哪条证据塞不进任何提案）+ `critique-usability.json`（这个模型对使用者好不好导航）。**最终模型是批评促成的收敛综合**：A 的工件脊柱 + B 的断言目录 + C 的反馈边模型。

真实性已核验：`00.json` 声称 `ActionStart` 锚在 `coreaction.cc:5624`——取 `ed1ae4d8` 时点的 `coreaction.cc` 第 5620–5635 行，实际正是 `universalAction` 注册块的 `new ActionStart("base")` … `new ActionPrototypeTypes("protorecovery")`。锚点逐行对得上。

**关键实例（批评逼出模型缺口的形态）**：`critique-coverage.json` 第一条——Ghidra 的 `stageJumpTable` 是"在克隆上跑一套**不同的**精简 action 集然后丢弃"的递归子反编译，提案 A 的"工件弄脏了"边模型**表达不了它**（没有任何 S2 工件被弄脏——是构造了一个临时 Funcdata、简化、丢弃）。批评迫使新增第 9 种反馈边 `(c′) reduced-pipeline sub-query`——这个边后来变成 kuna 的 `pipeline <variant>` console 命令。**塞不进任何提案的证据就是新机制类型的来源。**

分工：人工做 schema 设计、切面划分、锚点抽查、最终综合；agent 做全部读码输出（每份 36 KB、45 步 pipeline 带 anchor，人工不可能也不必手写）。

#### 原版对三家的评价（综合 stage-model.md 角色表 + evidence insights + 阶段 2 决策篇）

**正式评价**（stage-model.md "Role in this study"，一家一句）：

| 反编译器 | 原文角色定义 | 中文解读 |
|---|---|---|
| Ghidra（C++） | "The codebase kuna extracts; the model's primary target" | 被抽取的代码基、模型的主要对象——"宿主/原材料"。别处的评价："The C++ engine is **excellent** but hard to study, instrument, and extend"——引擎优秀，作为 agent-first 产品的载体不合格 |
| angr | "Highest output quality; richest feedback machinery (SAILR)" | 输出质量最高、反馈机制最丰富 |
| Reko | "Simple baseline; clearest interprocedural (SCC) model" | 简单基线、过程间（SCC）模型最清晰 |

这个分工**直接塑造了 kuna**：Ghidra 出骨架（代码就是从它移植的）、angr 出质量和反馈思想（DIV-4 起 14+ 个特性移植：loweredswitch/namestyle/regionstructure/stackguard…）、Reko 出方法论对照（SCC 模型被引用但未直接采用）。

**逐家判断**（evidence 报告 insights 提炼）：

- **Ghidra**——调度最成熟，但边界消失、无回滚。最强处：Action/Rule 双层引擎（"Rule vs Action 区分对可扩展性是关键的"——Action 顺序应用于整个函数，Rule 进池按 opcode 索引逐 op 应用）；group 成员制是定制主杠杆；mainloop 双重重复到不动点的 quiescence 模式被 kuna 原样继承。批评：Band B 四个工件**在代码里没有阶段边界**（"no inter-stage boundary exists in the code"）；goto 放置**贪婪、无回滚**（对比 angr）。它给 kuna 的：整个引擎代码 + 差分 oracle。
- **angr**——质量和反馈机制之王，但有已知代价。最强处：RegionIdentifier/Phoenix/SAILR 结构化子系统 + **speculate-validate-rollback 反馈边 (e)**——"编辑图 → 重跑 RegionIdentifier → 量 goto 数 → 接受或回滚"，三家唯一带质量门的回滚；KnowledgeBase 干预模型 + options 暴露面最完整。批评：Clinic 12 个子阶段依赖关系微妙；Dephication 的 vvar 映射固定在一个时点不重算。它给 kuna 的：质量参照系（decbench 里 kuna 35.93% vs angr 34.20% GED 完美率——**kuna 已超过老师**）+ 十几个移植特性 + "quality goto 度量"这个流水线评分基础。
- **Reko**——最清晰的对照标本。最强处：SCC 过程间模型三家最清晰；用户干预**逐地址粒度**（对比全局旗标）。批评：反馈机制**散乱无统一框架**；类型重建与扫描/数据流解耦到**不回流**——结构性弱点。它给 kuna 的：对照组——证明"同一模型可以有不同调度 regime"，这是"Band B 内顺序是调度 regime、不属于模型本身"这条设计的直接证据。

**最有评价力度的一句**（模型设计辩护词，stage-model.md）："Any strict order among the middle analyses is a **fiction**…A taxonomy must describe the dependency structure **without canonizing either schedule**"（中间分析的任何严格顺序都是虚构；分类学必须描述依赖结构而不把任何一家的调度奉为正典）——Ghidra 的 mainloop 共演化是事实但不是真理，angr 的分阶段求解也是事实但不是真理；**P0–P9 + Band B 是同时容纳两者的抽象**。

**kuna 的自我定位收尾**：Ghidra 是起点和 oracle，angr 是质量和思想来源，Reko 是方法论对照——而 kuna 自己的位置是 "agent-first"：三家都**没把"agent 当作用者"设计进去**（angr 的 KnowledgeBase 最接近但也不是产品中心）——这正是 kuna 填的空。

#### 1b. 重现操作

1. 对 Ghidra（C++ 源码可得）、angr、Reko 各做结构走读。产出物**按原版形态**：
   - 每阶段一份证据 JSON（该阶段输入什么、产出什么工件、代码在哪个文件）；
   - 工件/决策点/调度三张正交表；
   - 两份自我批评（我漏了什么、这个模型好不好用）。
   - **具体操作**（对应 1a 的机制）：并行派 10 个 agent 各读一个切面 → 人工抽查锚点（抽样核对 anchor 行号对不对得上源码）→ 派 ≥3 个 agent 提竞争提案（透镜强制不同）→ 派 2 个对抗批评者 → 人工综合。
2. 写出你的一屏模型（`phases.md` 形态）+ 详版（`stage-model.md` 形态）。
3. **决定性判断**：P0 正交平面、Band B 不动点带、反馈边类型集、HARD/HINT 断言强度——这四样定义了后面所有 option 的语义空间，错了后面全返工。
- 验收标准：能把 vendored C++ 树的**每一个文件**映射到一个阶段（原版映射了 115 个文件，`288ab127`）。映射不出来的文件就是模型缺口。

### 步骤 2（人工+agent）：第一个分歧原型

#### GH-558 的来源与选题标准（原版考证）

**来源链条**：GH-558 = NationalSecurityAgency/ghidra#558，"Don't change conditions to equivalent expressions during decompilation"——**2019 年开，2025–2026 仍复现在 11.3/12.x**。内容：`x <= 8` 被反编译成 `x < 9`（Band B 简化器把每个 LESSEQUAL-with-constant 规范化成 constant±1 的 LESS，**分析用的规范化形式泄漏进最终 C**；评论者还指出 `2^n` 源常量因此显示成 `2^n - 1`）。

**进入 kuna 的通道**：issue 战役素材不直接爬 GitHub，而是来自 **PHADE issue 数据集**（`~/github/PHADE/issue_dataset/ghidra/issues/*.json`，mahaloz 自有工具链）——每个 issue 已在 Ghidra 12.1 上**预复现并结构化**（`repro.status == "reproduced"`、`repro.method`（C/disasm/pcode）、arch、raw_hex 最小机器码等 JSON 字段）。58 个复现成功的进入工作范围，GH-558 是其一。

**PHADE 公开性考证（2026-09-02 查证）**：**未公开**。web 搜索 "PHADE" + mahaloz/ghidra/issue dataset 零结果——无同名 GitHub 仓库、无论文、无 Zenodo 条目；kuna 仓库内也只在 `tests/stages/README.md:4` 出现一次（本地路径 `~/github/PHADE/...` 是 mahaloz 机器上的私有工作台）。issue 本身全部来自公开 ghidra issue tracker，**PHADE 只是把"复现"这步前置成了数据集**——不可公开获得的是复现劳动，不是素材。注意别混淆：USENIX Security '24 论文 *"A Taxonomy of C Decompiler Fidelity Issues"*（Dramko et al., CMU/SEI）有公开数据集（zenodo.org/records/8419614），但那是"4 个反编译器的保真度缺陷人工分类学"，与 PHADE 的"issue 复现数据集"不是同一个东西。

**为什么选它做第一个**（`docs/prototypes/gh558.md`，commit `64bb80aa` 写明）：它是**纯表示策略**的理想靶子——`x <= 8` 和 `x < 9` **语义都对**，Ghidra 修不了它因为没有 bug 可修。按阶段模型，这是"**未被暴露的子阶段决策**"，不是 bug；要"修"只能靠把决策拆成命名、可断言控制的细粒度阶段。选它把两个问题解耦：先验证"阶段模型能否暴露决策"，不掺杂"能否修 bug"。**若阶段模型连这种最纯的情况都处理不了，它就处理不了任何情况。**

**修复形态**（阶段模型的第一次实证成功，全部模式在此定型）：
- `RuleIntLessEqual` 从 132 条规则的大杂烩 `analysis` 组拆出，命名 `canonicalcompare` 组（五个管线变体全挂，默认行为不变）；
- 新增 kuna 自有 `kuna_compareform.{hh,cc}` 实现 `presentcompare`：把带标记的 `V < c+1` 还原回 `V <= c`（ElementId **4000**——第一个 4000+ 自有 id）；
- **溯源机制**：规范化原语 `Funcdata::replaceLessequal` 给改写后的 op 打 addlflags 位（**0x1000**，第一个 0x1000+ 自有位）——"Band B 的规范化跨界到 S9 时必须可逆，**溯源是子阶段拆分得以实现的前提**"；
- `option compareform canonical|original`，默认 canonical = 与上游逐字节一致；
- 同一 issue 的次要抱怨（`p->r[i]` 渲染成 `*(p->r + i)`）定位为 **LATENT S9 决策** → 第二个 option `arraynotation`（4001）——**一个 issue 拆出两个决策点**的第一次实践。

**重现含义**：不需要 PHADE——直接从 Ghidra 官方 issue 列表按标签/arch 筛选即可（但保留"先复现、复现不进不修"的纪律；PHADE 只是把复现工作前置了）。第一个测试对象的选择标准：**两种输出都语义正确、纯粹是表示偏好的 issue**——把"能否暴露决策"和"能否修 bug"解耦，先验证前者。

#### 操作步骤

1. 挑一个真实公开 issue（按上述选题标准：纯表示策略优先）；
2. agent 复现、定位到子阶段决策点；人工审查"这确实是决策点而不是硬 bug"；
   - 复现先**内嵌最小机器码**（原版 `gh558-compareform.xml` 的 bytechunk 直接内嵌 16 字节：`83ff087f...`），第一遍断言默认输出确实是 bug 形态；
3. agent 实现第一个 option（`compareform canonical|original` 形态）+ 双向 `tests/stages/gh*.xml`；
   - 涉及"分析规范化泄漏到输出"类的决策，先建**溯源机制**（标记位），再建还原动作——没有溯源，还原无从谈起；
4. 写 before/after 演示脚本；
   - 原版附带做了**实验性消融**：`compareform original` 全局强推 → 12/675 断言变化（纯文本形态）；`canonicalcompare` 从管线剔除 → 另一个 9/675 变化（下游规则依赖规范形式）——**两个不同的决策，两份不同的证据**，这正是"分析用规范化"与"给人看的呈现"必须拆成两个子阶段的实证。
5. 人工决定默认值 → 若翻转记 DIV-1；
   - 原版这次**没有翻转**（默认 canonical 保持逐字节一致）——`docs/prototypes/gh558.md` 的诚实评估写明："no behavior fixed; decisions exposed; per-op assertion grain recorded as future work"。第一个原型的价值是**验证模型**，不是改变行为。
- 验收标准：`make test` 仍 675/675；`make test-stages` 双向通过（off 断言 bug、on 断言修复）；upstream 输出在默认 option 下逐字节不变。

### 步骤 3（agent，人定接口）：控制面基础设施

按原版清单建（这是后面 agent 能"自主"的根，语义必须人工定义清楚）：

- 阶段注册表（模型→可查询数据）；
- console 自注册 + `kassert`（类型化断言 API，报告最小回卷范围）；
- restart 观测（为什么重启）；
- `quality` goto 质量度量（流水线的评分基础）；
- `catalog` JSON（LLM 控制面：agent 自发现全部决策点）。
- 验收标准：`kuna catalog --json` 列出全部已知决策点，每个带 use_when/values/example；`kassert` 一次断言可驱动一次完整重跑。

### 步骤 4（agent 执行，人工抽查）：issue 战役

1. 收集公开 Ghidra issue（或你自己复现的），逐个**先复现**（复现不进 bug 修复——单独复现提交）；
2. 对复现集做 triage 分桶：spec-fix（改 .slaspec）/ stage-exposure（挂 option）/ not-viable / already-correct——**先分桶再动手，成本上限由桶决定**；
3. spec-fix 波：agent 直接修 spec + 写测试（无 option，严格纠错）；
4. stage-exposure 波：每个都是"option 默认关 + 双向测试"；
5. 每修一个跑四门（此时是三门：`make test` / `make test-stages` / spec 相关检查）。
6. **人工节点**：每个默认值翻转都要看消融证据。参考原版 DIV-2 的裁决形态——8 开、2 拒（有发散证据）、1 加护栏。
- 验收标准：37 个量级的 issue 处理完后，`make test` 全程 675/675 无一次重钉；每个翻转有 DIV 行 + 消融数字。

### 步骤 5（agent，人批准方向）：第一个跨反编译器特性移植

- 从 angr（或你选的参考）挑一个启发式简化器（原版：LoweredSwitchSimplifier）；
- agent 移植成 `kuna_<slug>.<语言>` 模块 + option + 测试 + 消融 + 速度测量；
- 人工看消融决定默认（原版：DIV-4，0/675 + 结构护栏 → 默认开）。
- 验收标准：这是阶段 3 流水线的"第一个数据点"——它的 bundle 形态（analysis/demo/record/DIV）就是之后每个 PR 的模板。

### 步骤 6（人工）：阶段 1 出口检查

- [ ] 阶段模型成文且每个文件有归属；
- [ ] 控制面五件套（registry/console/kassert/restartlog/quality/catalog）可用；
- [ ] issue 战役结束：每个修复有测试、每个默认翻转有 DIV 行和消融证据；
- [ ] 第一个 angr 移植落地，bundle 形态确立；
- [ ] **全程 `baseline.json` 未被重钉过一次**；
- [ ] 你现在拥有一切前置去启动阶段 2（Rust 移植：wave 底稿=文件映射表，差分 harness=675 断言 + stages 双语料）。

## 四、关键教训（从原版过程的证据里提炼）

1. **模型先于一切自动化**：流水线（06-09）能在启动当天就合入第一个 PR，是因为阶段模型、kassert、quality、catalog 在前一天都已就位——agent 自主的前提是控制面完备。
2. **消融先于默认**：DIV-2 的形态（8 开 2 拒 1 护栏）说明默认值决策必须是**证据裁决**不是品味裁决——v850indirectbranch 的"无界跳台子查询"发散是消融发现的，不是 review 发现的。
3. **先分桶再动手**：46 个剩余 issue 先机械 triage（20/12/13/1）再修，防止 not-viable 的浪费。
4. **自有测试与 oracle 物理隔离**：`tests/stages/` 独立目录 + 独立 baseline——上游 oracle 保持神圣是差分方法论的根。
5. **阶段 1 全在 C++ 侧**：Rust 移植（06-10 起）之前，kuna 的价值已经存在于"C++ 树 + 控制面 + 测试语料"里。重现时不要急于换语言——先让方法论在 oracle 树旁边长出来。
